RemotiveTopology

Run RemotiveTopology vehicle-system simulations ("system of systems") on ephemeral GCE VMs. A topology instantiates a platform of ECUs, CAN buses, and recorded or simulated traffic via RemotiveBroker — from a single restbus to a full virtual car with a Cuttlefish IHU.

Workflows

  • remotive-builder-image — build the container image used by the other workflows (packer, gcloud, kubectl). Run once first.
  • remotive-instance-template — bake the golden VM image (Docker, remotivebus, remotive CLI) with Packer and publish the GCE instance template. Run before the first launch and after dependency updates.
  • remotive-launcher — boot an ephemeral VM from the template, build and start a topology (default: the vendored getting_started project, or any project via topologyDownloadUrl), optionally run its tests, keep it alive for interactive access, then tear down. Logs and results land in GCS.

One-time setup: RemotiveCloud credentials

Topology builds authenticate against RemotiveCloud. Create a Secret in the workflows namespace with a revocable, least-privilege service-account token (never personal credentials): 

kubectl -n <prefix>workflows create secret generic workflow-remotive-cloud-auth \
  --from-literal=token=<service-account-token> \
  --from-literal=organization=<organization-id>

Accessing a running topology

All interactive access goes through MTK Connect, which requires the workflow-mtk-connect-apikey Secret in the workflows namespace (created by the mtk-connect module). While a launch is in its keep-alive window, the testbench (remotive-launcher-<n>) exposes RemotiveStudio (port 57123) and the topology's forward_ports as raw TCP tunnels, plus a HOST terminal on the VM. Topologies that declare adb_devices instead register one MTK Connect Android device per entry, with live screen streaming, adb terminal, logcat and touch input.
